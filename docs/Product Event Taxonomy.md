# Product Event Taxonomy

## Purpose

This document defines the business events used throughout this project.

The objective is to establish a common event language before designing event schemas, generating synthetic data, or building analytics pipelines.

Every downstream component—including SQL models, dashboards, and data quality validation—depends on the event definitions documented here.

This document serves as the foundation for all Product Analytics activities in this project.

---

# Product Overview

This project simulates a subscription-based Software-as-a-Service (SaaS) platform.

Users can:

- Visit the website
- Register an account
- Log in
- Explore product features
- Upgrade to a paid subscription
- Manage their subscription

The platform continuously generates event data throughout the customer lifecycle.

These events become the foundation for:

- Product Analytics
- KPI Calculation
- Dashboard Reporting
- Data Quality Validation
- Root Cause Investigation

# Event Categories

Business events are organized into the following domains.

## Acquisition

Events generated before user registration.

Examples:

- Landing Page View
- Marketing Campaign Visit
- Referral Visit

---

## Authentication

Events related to user identity.

Examples:

- Sign Up
- Login
- Logout
- Password Reset

---

## Engagement

Events generated while users interact with product features.

Examples:

- Feature View
- Feature Click
- Search
- Navigation

---

## Conversion

Events representing business value creation.

Examples:

- Upgrade Plan
- Checkout Started
- Subscription Activated

---

## Billing

Events related to payment and subscription management.

Examples:

- Payment Success
- Payment Failed
- Subscription Renewed
- Subscription Cancelled

---

## System

Technical events generated by the platform.

Examples:

- API Error
- Tracking Failure
- Timeout
- Page Error

---

# Event Priority

Not every event has the same business importance.

Critical business events should receive stricter validation rules and monitoring.

| Priority | Description |
|----------|-------------|
| Critical | Business KPIs cannot be calculated without this event. |
| High | Strong impact on Product Analytics and conversion analysis. |
| Medium | Useful for behavioral analysis and feature adoption. |
| Low | Supplemental information with limited business impact. |

# Design Principles

## 1. Business First

Events should represent meaningful business activities rather than implementation details.

---

## 2. Consistent Naming

Each event should have one clear business meaning.

Duplicate event definitions should be avoided.

---

## 3. Analytics-Oriented

Every event should support at least one business KPI or analytics use case.

Events without analytical value should not be collected.

---

## 4. Data Quality by Design

Events should be designed with validation in mind.

Schema consistency, completeness, uniqueness, and ownership should all be considered before implementation.

---

## 5. Version Incrementally

Version 1.0 focuses on the minimum event set required to analyze the subscription conversion funnel.

Additional business events and system events will be introduced in future iterations as the platform evolves.
